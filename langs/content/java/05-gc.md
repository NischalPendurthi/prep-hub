## Reachability and GC roots {#ch05-roots .th}

An object is **live** if it can be reached by following references from a **GC root**. Everything else is garbage, no matter how many references point at it from other garbage, so cycles are never a problem in Java. The roots are:

- local variables and operand-stack entries in every thread's active frames;
- static fields of loaded classes;
- references held by native code (JNI global references) and by the JVM itself;
- live `Thread` objects and objects used as locks by running threads.

Collectors find live objects by **tracing** from the roots, not by counting references. That is the fundamental difference from CPython (Python chapter 4).

```java run=c05-reachability
import java.lang.ref.WeakReference;

public class Reachability {
    static class Node {
        Node next;
        final byte[] payload = new byte[1024];
    }

    static Object keepAlive;

    public static void main(String[] args) {
        Node a = new Node(), b = new Node();
        a.next = b;
        b.next = a;                                // a cycle
        WeakReference<Node> probe = new WeakReference<>(a);
        a = null;
        b = null;                                  // the cycle is now unreachable
        System.gc();
        System.out.println("cycle collected: " + (probe.get() == null));

        Node c = new Node();
        keepAlive = c;                             // a static field is a GC root
        WeakReference<Node> probe2 = new WeakReference<>(c);
        c = null;
        System.gc();
        System.out.println("reachable from a static: " + (probe2.get() != null));
    }
}
```

`System.gc()` is only a request, but with G1 it normally triggers a full collection, which makes it useful in small demos and almost always wrong in production code (it can be disabled with `-XX:+DisableExplicitGC`). A `WeakReference` does not keep its target alive, so it reports whether the object survived.

## Generational collection {#ch05-generations .th}

The **weak generational hypothesis**: most objects die young, and old objects rarely point to young ones. HotSpot's collectors split the heap accordingly:

- The **young generation**: new objects are allocated in **eden** (through TLABs, Chapter 3). A **minor (young) collection** copies the few live objects out of eden into a **survivor** space and discards the rest of eden in one step. Its cost is proportional to the number of *live* objects, not to the garbage.
- Objects that survive several young collections (their **age**, kept in the mark word, reaches the tenuring threshold, at most 15) are **promoted** to the **old generation**, which is collected less often.
- A **card table** records which parts of the old generation have been written with references into the young generation, so a minor collection only needs to scan those cards instead of the whole old generation. Recording costs a **write barrier**: a few instructions added to every reference store.

```java run=c05-young nondet cmd="javac -d . Young.java && java -Xmx256m -Xlog:gc -cp . Young | grep -E 'Pause Young|Pause Full|done' | head -6"
public class Young {
    record Event(long id, String name) {}

    public static void main(String[] args) {
        Event[] recent = new Event[1000];
        long sum = 0;
        for (long i = 0; i < 20_000_000; i++) {
            Event e = new Event(i, "event");
            recent[(int) (i % recent.length)] = e;      // only the last 1000 stay alive
            sum += e.id();
        }
        System.out.println("done " + (sum > 0));
    }
}
```

Twenty million objects pass through the heap. Each young pause takes a few milliseconds and shrinks the heap from over 100 MB back to about 1 MB (`147M->1M`), because almost nothing in eden is still alive when it runs: the pause copies only the last thousand events.

## G1: the default collector {#ch05-g1 .th}

**G1** (Garbage-First), the default since Java 9, divides the heap into equal-sized **regions** (1 to 32 MB, chosen from the heap size). Each region is, at any time, eden, survivor, old, humongous or free. That lets G1:

- collect the young generation by **evacuating** (copying) live objects from all eden and survivor regions into new regions, a stop-the-world pause run by several parallel threads;
- run **concurrent marking** of the old generation while the application keeps running, when the heap's occupancy passes a threshold (45% by default, adapted at run time);
- then run **mixed collections** that evacuate young regions plus the old regions with the most garbage first (hence "Garbage-First"), choosing how many regions to take so that each pause stays near the target set by `-XX:MaxGCPauseMillis` (200 ms by default);
- treat any object of half a region or more as **humongous**, allocated directly in contiguous old regions.

```java run=c05-g1-init cmd="javac -d . Init.java && java -Xmx256m -Xlog:gc+init -cp . Init | grep -E 'Region Size|Max Capacity|Compressed Oops' | sed 's/^\[[^]]*\]\[[^]]*\]\[[^]]*\] //'"
public class Init {
    public static void main(String[] args) {
        System.out.println(Runtime.getRuntime().maxMemory() / (1 << 20) + " MB usable");
    }
}
```

With a 256 MB heap the regions are 1 MB, so any single array of 512 KB or more is humongous.

### Stop-the-world and safepoints

A collector that moves objects must update every reference to them, including references in registers and stack frames, so the application threads must stop at a point where the JVM knows exactly where every reference is. Those points are **safepoints**: method returns, loop back-edges and allocation sites, where compiled code checks a polling page. The JVM sets a flag, waits until every thread reaches a safepoint, does its work, and releases them.

The pause includes **time to safepoint**: a thread in a long counted loop that the JIT compiled without safepoint polls (loop strip-mining limits this in modern JVMs) can delay every other thread. Safepoints are also used for other VM operations: deoptimisation, thread dumps, biased-lock revocation in older JVMs, class redefinition.

## ZGC and the other collectors {#ch05-zgc .th}

| Collector | Flag | Design | Best for |
|---|---|---|---|
| Serial | `-XX:+UseSerialGC` | One thread, stop-the-world young and old | Small heaps, single-core containers |
| Parallel | `-XX:+UseParallelGC` | Many threads, stop-the-world | Batch jobs that want maximum throughput |
| G1 | default | Regions, concurrent marking, pause target | General purpose |
| ZGC | `-XX:+UseZGC` | Concurrent marking **and** relocation, coloured pointers, load barriers | Large heaps with sub-millisecond pauses |
| Shenandoah | `-XX:+UseShenandoahGC` | Concurrent compaction with barriers (in some OpenJDK builds) | Low pauses |

**ZGC** does almost all its work, including moving objects, while application threads run. It stores metadata bits in each reference ("coloured pointers") and inserts a **load barrier** on every reference read: if a reference is stale (its object has been or is being relocated), the barrier fixes it up on the spot. Pauses no longer grow with heap size or the number of live objects and stay well under a millisecond, at the cost of some throughput and memory. ZGC became generational in JDK 21 with `-XX:+ZGenerational` (JEP 439), generational by default in JDK 23 (JEP 474), and the non-generational mode was removed in JDK 24.

```java run=c05-collectors cmd="javac -d . Which.java && for gc in -XX:+UseSerialGC -XX:+UseParallelGC -XX:+UseG1GC -XX:+UseZGC; do java $gc -cp . Which; done"
import java.lang.management.*;
import java.util.stream.Collectors;

public class Which {
    public static void main(String[] args) {
        System.out.println(ManagementFactory.getGarbageCollectorMXBeans().stream()
            .map(GarbageCollectorMXBean::getName).collect(Collectors.joining(", ")));
    }
}
```

Each collector registers its own management beans, which is how monitoring tools tell which one a JVM is running.

## Reference types {#ch05-references .th}

`java.lang.ref` gives four strengths of reference:

- **Strong**: an ordinary reference; keeps the object alive.
- **Soft** (`SoftReference`): cleared only when the JVM needs memory, before it throws `OutOfMemoryError`. Once used for caches, but they make memory use unpredictable; prefer a bounded cache.
- **Weak** (`WeakReference`, `WeakHashMap`): cleared at the next collection that finds the object only weakly reachable. Used for canonicalising maps and metadata attached to objects you do not own.
- **Phantom** (`PhantomReference`): `get()` always returns `null`; the reference is enqueued after the object is unreachable, so you can clean up associated native resources. `java.lang.ref.Cleaner` (Java 9) wraps this in a simple API.

```java run=c05-refs
import java.lang.ref.*;
import java.util.*;

public class Refs {
    static class Resource {
        final String name;
        Resource(String name) { this.name = name; }
    }

    public static void main(String[] args) throws Exception {
        Map<Object, String> meta = new WeakHashMap<>();
        Object key = new Object();
        meta.put(key, "metadata");
        System.out.println("before: " + meta.size());
        key = null;
        System.gc();
        Thread.sleep(50);
        System.out.println("after:  " + meta.size());

        Cleaner cleaner = Cleaner.create();
        List<String> log = Collections.synchronizedList(new ArrayList<>());
        Resource r = new Resource("socket");
        String name = r.name;                                // the action must not capture r itself
        cleaner.register(r, () -> log.add("cleaned " + name));
        r = null;
        for (int i = 0; i < 20 && log.isEmpty(); i++) { System.gc(); Thread.sleep(20); }
        System.out.println(log);
    }
}
```

The cleaning action must not refer to the object it cleans up after, or the object stays reachable through the cleaner forever. `Object.finalize()` is the older mechanism; it is deprecated for removal (JEP 421) because finalizers run late, on an unspecified thread, can resurrect objects and slow down every collection.

## How Java programs leak memory {#ch05-leaks .th}

Garbage collection removes the "forgot to free" leak, but not the "forgot to stop referencing" leak. Anything reachable from a root stays alive:

- **static collections** that only grow (caches without eviction, registries);
- **listeners and callbacks** registered and never removed;
- **`ThreadLocal`s** in thread pools: pooled threads live forever, so values set and never removed accumulate;
- **class-loader leaks** in redeployable applications: one static reference from a long-lived class to an object of the application keeps the whole application's loader and all its classes (in metaspace) alive;
- **unbounded queues** between a fast producer and a slow consumer.

```java run=c05-leak
import java.lang.ref.WeakReference;
import java.util.*;

public class Leak {
    static final List<Runnable> listeners = new ArrayList<>();

    static class Screen {
        final byte[] bitmap = new byte[1 << 20];
        Screen() { listeners.add(this::refresh); }      // captures this
        void refresh() {}
    }

    public static void main(String[] args) {
        WeakReference<Screen> probe = new WeakReference<>(new Screen());
        System.gc();
        System.out.println("screen leaked via listener: " + (probe.get() != null));
        listeners.clear();
        System.gc();
        System.out.println("after removing listener, collected: " + (probe.get() == null));
    }
}
```

The method reference `this::refresh` captures the `Screen`, and the static list keeps it alive along with its 1 MB bitmap. Heap dumps (`jcmd <pid> GC.heap_dump`) analysed with a tool such as Eclipse MAT show these paths from GC roots directly.

:::key
To find a leak, compare two heap histograms (`jcmd <pid> GC.class_histogram`) taken minutes apart under steady load: the class whose instance count keeps climbing is the leak, and a heap dump's "path to GC roots" shows who holds it.
:::

## Concept and tricky questions {#ch05-concept .dr}

:::drill concept
What makes an object eligible for garbage collection in Java? Do reference cycles prevent collection?
---
**Answer.** It is not reachable from any GC root (thread stacks, static fields, JNI references, live threads). Cycles do not matter: an unreachable cycle is collected like any other garbage.

**Why.** HotSpot's collectors trace from roots; they never count references.
:::

:::drill concept
Explain the weak generational hypothesis and how a young collection uses it.
---
**Answer.** Most objects die young. A young collection copies only the live objects out of eden (and the current survivor space) and reclaims the rest wholesale, so its cost depends on the number of survivors, which is small.

**Why.** Copying also compacts the survivors, so allocation can stay a pointer bump.
:::

:::drill concept
How does a young collection avoid scanning the whole old generation for references into the young generation?
---
**Answer.** A card table marks the parts of the old generation (cards of 512 bytes) that had reference fields written; a write barrier dirties the card on each reference store. The young collection scans only dirty cards (G1 additionally keeps per-region remembered sets).

**Why.** That is the cost the application pays for generational GC: a few extra instructions on every reference write.
:::

:::drill concept
Describe how G1 organises the heap and what `MaxGCPauseMillis` controls.
---
**Answer.** The heap is divided into equal regions with dynamic roles (eden, survivor, old, humongous, free). G1 evacuates young regions in stop-the-world pauses, marks the old generation concurrently, and in mixed collections evacuates the old regions with the most garbage first. `MaxGCPauseMillis` (default 200 ms) is a target G1 uses to size the young generation and choose how many old regions to include per pause.

**Why.** It is a goal, not a guarantee; an allocation rate that outpaces concurrent marking still ends in a full GC.
:::

:::drill tricky
What is a safepoint, and how can one thread make every thread's GC pause longer?
---
**Answer.** A point in the code where a thread's state (including where every reference is) is known to the JVM, so it can be stopped safely. Stop-the-world operations wait until all threads reach one. A thread running a long loop without safepoint polls delays the start of the pause for everyone (time to safepoint).

**Why.** `-Xlog:safepoint` shows time-to-safepoint; loop strip mining in modern JIT-compiled code inserts polls into long counted loops.
:::

:::drill concept
What does ZGC do differently from G1?
---
**Answer.** It relocates (compacts) objects concurrently with the application, using coloured pointers and a load barrier on every reference read that fixes up stale references. Pauses stay below a millisecond regardless of heap size; it trades some throughput and memory for that.

**Why.** It is generational from JDK 21 (opt-in) and by default from JDK 23.
:::

:::drill tricky
Can a Java program have a memory leak? Give two common causes.
---
**Answer.** Yes, when objects remain reachable even though they are no longer needed. Common causes: growing static collections or caches, listeners never removed, `ThreadLocal` values left in pooled threads, and class-loader leaks after redeployment.

**Why.** The GC frees only unreachable objects; it cannot know that you will never use a reachable one again.
:::

## Predict the output and find the bug {#ch05-reading .dr}

:::drill output
What does this print?

```java run=c05-d-weak
import java.lang.ref.*;

public class WeakDemo {
    public static void main(String[] args) {
        Object strong = new Object();
        WeakReference<Object> weak = new WeakReference<>(strong);
        SoftReference<Object> soft = new SoftReference<>(new Object());
        PhantomReference<Object> phantom = new PhantomReference<>(new Object(), new ReferenceQueue<>());
        System.gc();
        System.out.println((weak.get() != null) + " " + (soft.get() != null) + " " + phantom.get());
        strong = null;
        System.gc();
        System.out.println(weak.get());
    }
}
```
---
**Answer.** `true true null`, then `null`. The weak target is still strongly reachable through `strong`; the soft target survives because there is no memory pressure; `PhantomReference.get()` always returns `null`. After `strong = null`, the next GC clears the weak reference.

**Why.** Each reference type defines when the GC may clear it, not whether `get()` is useful.
:::

:::drill output
What does this print?

```java run=c05-d-local
import java.lang.ref.WeakReference;

public class Local {
    public static void main(String[] args) {
        byte[] big = new byte[10 << 20];
        WeakReference<byte[]> ref = new WeakReference<>(big);
        big = null;
        System.gc();
        System.out.println("collected after nulling: " + (ref.get() == null));
        String s = new String("temp");
        WeakReference<String> sref = new WeakReference<>(s);
        System.gc();
        System.out.println("still alive while the local is in use: " + (sref.get() != null) + " " + s.length());
    }
}
```
---
**Answer.** `collected after nulling: true`, then `still alive while the local is in use: true 4`. A local that is still used later is a root; once nothing refers to the array, it can be collected.

**Why.** In JIT-compiled code a local whose last use has passed may be considered dead before the method ends, so "set it to null" is rarely needed; the interpreter is more conservative. `Reference.reachabilityFence` exists for the rare case where you must keep something alive.

:::drill output
Which of these statements make the `Order` object eligible for collection right after the line runs, assuming nothing else refers to it?

```java run=c05-d-eligible
import java.lang.ref.WeakReference;
import java.util.*;

public class Eligible {
    static class Order { final byte[] data = new byte[1024]; }
    static List<Order> registry = new ArrayList<>();

    static boolean collected(WeakReference<?> r) {
        System.gc();
        return r.get() == null;
    }

    public static void main(String[] args) {
        Order o1 = new Order();
        registry.add(o1);
```

**Answer.** `in static list: false`, then `removed from local map: true`. The static `registry` is a root, so the first order stays alive after `o1 = null`. The second is unreachable once removed from the map.

**Why.** Nulling one reference does not free an object that another live reference still holds.

:::drill bug
A request-scoped value leaks between users in a thread pool, and memory grows. Find and fix the bug.

```java run=c05-d-bug-threadlocal
import java.util.concurrent.*;

public class ThreadLocalLeak {
    static final ThreadLocal<String> CURRENT_USER = new ThreadLocal<>();

    static String handle(String user, boolean authenticated) {
        try {
            if (authenticated) CURRENT_USER.set(user);
            return "served " + CURRENT_USER.get();
        } finally {
            CURRENT_USER.remove();
        }
    }

    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newSingleThreadExecutor();
        System.out.println(pool.submit(() -> handle("alice", true)).get());
        System.out.println(pool.submit(() -> handle("bob", false)).get());
        pool.shutdown();
    }
}
```
---
**Answer.** Without the `finally { CURRENT_USER.remove(); }`, the pool's thread keeps alice's value after her request, so bob's unauthenticated request is served as alice, and every value set stays reachable from the long-lived thread. Always `remove()` in a `finally`.

**Why.** A `ThreadLocal` value lives as long as its thread; pooled threads live as long as the pool. Java 21's `ScopedValue` (preview) makes the scope explicit.
:::

:::drill bug
A cache built on `SoftReference`s causes long full GCs and unpredictable heap usage under load. What is wrong with the design, and what is better?

```java run=c05-d-bug-soft
import java.util.*;

public class BoundedCache {
    static <K, V> Map<K, V> lru(int max) {
        return new LinkedHashMap<>(16, 0.75f, true) {
            @Override protected boolean removeEldestEntry(Map.Entry<K, V> e) { return size() > max; }
        };
    }

    public static void main(String[] args) {
        Map<Integer, byte[]> cache = lru(100);
        for (int i = 0; i < 10_000; i++) cache.put(i, new byte[1024]);
        System.out.println(cache.size() + " entries, oldest key " + cache.keySet().iterator().next());
    }
}
```
---
**Answer.** Soft references are cleared only under memory pressure, so the heap fills up to its limit with cache entries, every collection has to process them, and the cache's effective size depends on GC timing. A bounded cache with explicit eviction (an LRU map as above, or a library such as Caffeine) keeps memory predictable.

**Why.** Let the cache decide what to evict by policy, not the collector by memory pressure.
:::

## Write the code {#ch05-coding .cd}

:::drill code rating=1400
Write a `ResourcePool` that tracks native-like handles: each `Handle` must be closed explicitly, and if a caller forgets, a `Cleaner` reports the leak and releases the handle. Show both paths.
---
```java run=c05-c-cleaner
import java.lang.ref.Cleaner;
import java.util.*;
import java.util.concurrent.atomic.AtomicInteger;

public class Handles {
    static final Cleaner CLEANER = Cleaner.create();
    static final AtomicInteger open = new AtomicInteger();
    static final List<String> leaks = Collections.synchronizedList(new ArrayList<>());

    static final class Handle implements AutoCloseable {
        private static final class State implements Runnable {
            final int id;
            boolean closedExplicitly;
            State(int id) { this.id = id; }
            @Override public void run() {
                if (!closedExplicitly) leaks.add("handle " + id + " was not closed");
                open.decrementAndGet();
            }
        }
        private final State state;
        private final Cleaner.Cleanable cleanable;

        Handle(int id) {
            state = new State(id);
            cleanable = CLEANER.register(this, state);
            open.incrementAndGet();
        }

        @Override public void close() {
            state.closedExplicitly = true;
            cleanable.clean();                 // runs State.run() at most once
        }
    }

    public static void main(String[] args) throws Exception {
        try (Handle h = new Handle(1)) { }
        new Handle(2);                         // forgotten
        for (int i = 0; i < 50 && open.get() > 0; i++) { System.gc(); Thread.sleep(20); }
        System.out.println("open=" + open.get() + " leaks=" + leaks);
    }
}
```

The `State` object is a static nested class, so it holds no reference to its `Handle`; that is what lets the `Handle` become unreachable. `cleanable.clean()` makes explicit and implicit cleanup share one code path that runs once.
:::

:::drill code rating=1300
Write a tiny "mark and sweep" simulator: objects with ids and outgoing references, a root set, `mark()` by depth-first search from the roots, and `sweep()` that returns the ids of unreachable objects, including an unreachable cycle.
---
```java run=c05-c-marksweep
import java.util.*;

public class MarkSweep {
    static final class Obj {
        final int id;
        final List<Obj> refs = new ArrayList<>();
        boolean marked;
        Obj(int id) { this.id = id; }
    }

    static void mark(Collection<Obj> roots) {
        Deque<Obj> stack = new ArrayDeque<>(roots);
        while (!stack.isEmpty()) {
            Obj o = stack.pop();
            if (o.marked) continue;
            o.marked = true;
            for (Obj r : o.refs) if (!r.marked) stack.push(r);
        }
    }

    static List<Integer> sweep(List<Obj> heap) {
        List<Integer> freed = new ArrayList<>();
        for (Iterator<Obj> it = heap.iterator(); it.hasNext(); ) {
            Obj o = it.next();
            if (!o.marked) { freed.add(o.id); it.remove(); }
            else o.marked = false;             // reset for the next cycle
        }
        return freed;
    }

    public static void main(String[] args) {
        List<Obj> heap = new ArrayList<>();
        for (int i = 0; i < 7; i++) heap.add(new Obj(i));
        heap.get(0).refs.add(heap.get(1));
        heap.get(1).refs.add(heap.get(2));
        heap.get(3).refs.add(heap.get(4));      // 3 <-> 4: unreachable cycle
        heap.get(4).refs.add(heap.get(3));
        heap.get(5).refs.add(heap.get(0));      // 5 points into live data but is not a root
        mark(List.of(heap.get(0), heap.get(6)));
        System.out.println("freed " + sweep(heap) + ", live " + heap.stream().map(o -> o.id).toList());
    }
}
```

An explicit stack avoids recursion depth limits on long chains, which is also why real collectors use mark stacks. Being referenced *from* garbage (object 5 → 0) does not matter; only reachability *from roots* does.
:::

:::drill code rating=1200
Measure the effect of object lifetime: allocate 50 million small objects where (a) each dies immediately and (b) a large fraction is kept in a growing list, and print the GC count and total GC time from `GarbageCollectorMXBean`s for each.
---
```java run=c05-c-lifetime nondet cmd="javac -d . Lifetime.java && java -Xmx512m -cp . Lifetime"
import java.lang.management.*;
import java.util.*;

public class Lifetime {
    record Point(long x, long y) {}

    static long[] gcStats() {
        long count = 0, time = 0;
        for (GarbageCollectorMXBean b : ManagementFactory.getGarbageCollectorMXBeans()) {
            count += Math.max(0, b.getCollectionCount());
            time += Math.max(0, b.getCollectionTime());
        }
        return new long[] {count, time};
    }

    public static void main(String[] args) {
        long[] s0 = gcStats();
        Point[] ring = new Point[256];
        for (long i = 0; i < 50_000_000; i++) ring[(int) (i & 255)] = new Point(i, i);
        long[] s1 = gcStats();
        List<Point> kept = new ArrayList<>();
        for (long i = 0; i < 5_000_000; i++) kept.add(new Point(i, i));
        long[] s2 = gcStats();
        System.out.printf("short-lived: %d GCs, %d ms%n", s1[0] - s0[0], s1[1] - s0[1]);
        System.out.printf("long-lived:  %d GCs, %d ms (%d objects kept)%n", s2[0] - s1[0], s2[1] - s1[1], kept.size());
    }
}
```

Ten times fewer objects, but because they stay alive the collector has to copy them repeatedly and promote them, which costs far more than reclaiming fifty million dead ones.
:::

## Cheat sheet {#ch05-cheatsheet .th}

- Live = reachable from roots (stack frames, statics, JNI refs, live threads); tracing, not counting; cycles are fine.
- Generational: eden → survivor → old (age up to 15); young collections copy survivors, cost ∝ live objects; card table + write barrier for old→young refs.
- G1 (default): regions 1–32 MB, evacuation pauses, concurrent marking at ~45% occupancy, mixed collections pick garbage-rich old regions; humongous ≥ ½ region; `MaxGCPauseMillis` default 200 ms (a goal).
- Safepoints: all threads must reach one for stop-the-world work; time-to-safepoint can dominate a pause.
- ZGC: concurrent relocation with coloured pointers + load barriers; sub-ms pauses; generational opt-in in 21, default in 23, only mode in 24.
- Serial, Parallel (throughput), G1, ZGC, Shenandoah — pick by heap size and pause needs.
- References: strong, soft (cleared under memory pressure), weak (next GC), phantom (post-mortem cleanup; `Cleaner`). `finalize` is deprecated for removal.
- Leaks = unwanted reachability: static collections, listeners, `ThreadLocal` in pools (always `remove()` in `finally`), class-loader leaks, unbounded queues.
- Tools: `-Xlog:gc*`, `jcmd <pid> GC.class_histogram`, `GC.heap_dump`, Eclipse MAT, JFR.
