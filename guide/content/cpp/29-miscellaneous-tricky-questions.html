OOP and object model traps

Drills

These questions look like inheritance trivia, but each one hides a rule about object layout, construction phases or name lookup. Background is in Ch 1, Ch 2 and Ch 3.

Find the bugEach feed registers a tick callback in its constructor. After the second emplace_back, the first feed's callback misbehaves. Why?

#include <cstdio>
#include <functional>
#include <string>
#include <utility>
#include <vector>

class Feed {
public:
    explicit Feed(std::string name) : name_(std::move(name)) {
        on_tick = [this](double px) { std::printf("tick %.2f for a %zu-char feed\n", px, name_.size()); };
    }
    std::function<void(double)> on_tick;

private:
    std::string name_;
};

int main() {
    std::vector<Feed> feeds;
    feeds.emplace_back("XNAS-primary-equities-feed");
    feeds.emplace_back("XLON-primary-equities-feed");  // grows: feeds[0] is moved
    feeds[0].on_tick(101.25);
}
Answer

Answer. The lambda captures this, the address of the object under construction. When the vector grows from capacity 1 to 2, it move-constructs feeds[0] into the new buffer and frees the old one. The implicit move constructor moves on_tick as a value, so the new object's callback still holds the old address, and calling it reads name_ from freed memory. ASan reports heap-use-after-free. Without ASan it prints a plausible line, here a 0-character name, purely by luck.

Why. Implicit copy and move copy member values, and a value that points back into the object itself (a captured this, a self-pointer, an iterator into one of its own members) is stale in the copy. The same happens on any relocation: std::sort, std::swap, or returning the object without elision. The usual wrong answer blames std::function, which copied the lambda correctly. Fixes: pass the object to the callback instead of capturing it (std::function<void(Feed&, double)>); or make the class non-copyable and non-movable and keep it in a container that never relocates (std::deque, std::list, std::vector<std::unique_ptr<Feed>>); or rebind the callback in hand-written copy and move constructors. Capturing this in a thread or timer callback has the same lifetime problem (OS guide ch 1).

OutputA non-virtual helper calls a virtual function. What does each phase print?

#include <cstdio>

struct Base {
    Base() { hello("ctor"); }
    virtual ~Base() { hello("dtor"); }
    void hello(const char* when) const { std::printf("%s: %s\n", when, name()); }
    virtual const char* name() const { return "Base"; }
};

struct Derived : Base {
    Derived() { hello("Derived ctor"); }
    ~Derived() override { hello("Derived dtor"); }
    const char* name() const override { return "Derived"; }
};

int main() {
    Derived d;
    d.hello("main");
}
Answer
ctor: Base
Derived ctor: Derived
main: Derived
Derived dtor: Derived
dtor: Base

Why. During Base's constructor and destructor the object's dynamic type is Base ([class.cdtor]). The implementation makes this real by storing Base's vptr while the base constructor runs, switching to Derived's vptr once Derived's constructor starts, and switching back when ~Derived finishes. Calling through a helper does not get around it, because the helper reads the same vptr.

The common wrong answer is "ctor: Derived", from candidates who know Java or C#, where the override runs before the derived fields are initialised. C++ refuses to call into a derived part that does not exist yet (or no longer exists). If a base needs derived-specific setup, pass the data to the base constructor or use a two-phase factory.

OutputPredict all four sizes on a 64-bit Linux or macOS target. Two of them surprise most candidates.

#include <cstdio>

struct Plain  { long long x; char a; };
struct PlainD : Plain { char c; };

struct Poly  { virtual void f() {} char a; };
struct PolyD : Poly { char c; };

int main() {
    std::printf("Plain=%zu PlainD=%zu Poly=%zu PolyD=%zu\n",
                sizeof(Plain), sizeof(PlainD), sizeof(Poly), sizeof(PolyD));
}
Answer
Plain=16 PlainD=24 Poly=16 PolyD=16

Why. Plain is 8 + 1 bytes padded to 16, and Poly is an 8-byte vptr plus one char, also padded to 16. Both have 7 bytes of tail padding. The difference is what a derived class may do with those bytes. The Itanium C++ ABI (used by GCC and Clang on Linux and macOS) never reuses the tail padding of a base that is a POD in the C++03 sense, so PlainD::c goes at offset 16 and the class grows to 24. Poly is polymorphic and therefore not a POD, so its tail padding is fair game: PolyD::c sits at offset 9 and the size stays 16.

The rule exists because C code may memcpy a whole POD, padding included, which would overwrite a derived member living in that padding. The practical lesson: never memcpy or memset a base subobject with sizeof(Base), because for non-POD bases the derived class may own those bytes. MSVC uses a different ABI and gives different numbers, so say "on Itanium" when you answer. See Ch 1 for basic padding rules.

OutputA C library takes a callback and a void* context, and the strategy registers itself. What do the first two lines print on a 64-bit GCC or Clang target, and why would the callback crash without the second c_register?

#include <cstdio>

struct Logger {
    virtual ~Logger() = default;
    int level = 1;
};

struct Listener {
    virtual ~Listener() = default;
    virtual void on_event(int e) = 0;
};

struct Strategy : Logger, Listener {
    void on_event(int e) override { std::printf("event %d\n", e); }
};

// A C library stores a callback and an opaque context pointer.
static void (*g_cb)(void*, int);
static void* g_ctx;
static void c_register(void (*cb)(void*, int), void* ctx) { g_cb = cb; g_ctx = ctx; }

static void trampoline(void* ctx, int e) { static_cast<Listener*>(ctx)->on_event(e); }

int main() {
    Strategy s;
    c_register(trampoline, &s);  // Strategy* converted straight to void*
    Listener* good = &s;
    Listener* bad = static_cast<Listener*>(g_ctx);
    std::printf("offset of Listener: %td\n", reinterpret_cast<char*>(good) - reinterpret_cast<char*>(&s));
    std::printf("round trip correct: %d\n", bad == good);
    c_register(trampoline, static_cast<Listener*>(&s));  // the fix
    g_cb(g_ctx, 7);
}
Answer
offset of Listener: 16
round trip correct: 0
event 7

Why. Converting Strategy* to Listener* adjusts the address to the Listener subobject, which follows the Logger part (a vptr plus an int, padded to 16 bytes). Converting to void* does no adjustment: it is the address of the whole object, which is also the address of its Logger part. static_cast<Listener*>(void*) cannot know where the pointer came from, so bad points at the Logger subobject. Calling on_event through it loads Logger's vptr and calls whatever sits in that slot of Logger's vtable: undefined behaviour, in practice a crash or a call to the wrong function.

The rule: a round trip through void* is valid only when you cast back to exactly the type you converted from. So convert to the type the callback expects before erasing it, as the last c_register does. The wrong answer is "static_cast fixes up base offsets": it does so only between related class types, never from void*. With single inheritance the offset is 0 and the bug is invisible, so it appears the day someone adds a base class. The same applies to the arg of pthread_create, epoll_event.data.ptr and every C "user data" pointer.

TrickyTwo processes map the same shared memory region. The writer constructs a Quote there with placement new. Quote has a virtual price() and a std::string venue. The reader casts the region to Quote* and calls price(). What happens?

Answer

Answer. Undefined behaviour, and in practice a crash or garbage. The object contains pointers that only mean something in the writer: the vptr (the address of Quote's vtable in the writer's mapping of the executable) and the string's data pointer (into the writer's heap, or with SSO into the object at the writer's mapping address). With ASLR, the reader maps the executable and the shared region at different addresses, so the virtual call jumps through a wrong address and reading venue dereferences someone else's heap. It "works" when the reader is a forked child of the writer, or ASLR is off, which is exactly how such code passes its tests.

Why. std::is_trivially_copyable_v<Quote> is false: a class with virtual functions never has a trivial copy constructor, and that is the language telling you its bytes are not a self-contained value. Shared memory, files and network buffers need trivially copyable types without pointers: integers, fixed-size char arrays, offsets instead of pointers (as Boost.Interprocess's offset_ptr does), and an enum tag instead of a vptr, with each process dispatching on the tag itself. The reader also never created an object: for implicit-lifetime types, C++23's std::start_lifetime_as is the sanctioned way to say "treat these bytes as a T". A mutex or atomic placed in shared memory has its own rules (PTHREAD_PROCESS_SHARED, lock-free atomics only, OS guide ch 2).

OutputA dispatch table stores pointers to member functions. Is a call through &Venue::name virtual? And how big is the pointer?

#include <cstdio>

struct Venue {
    virtual ~Venue() = default;
    virtual const char* name() const { return "venue"; }
};

struct Nasdaq : Venue {
    const char* name() const override { return "nasdaq"; }
};

int main() {
    Nasdaq n;
    const Venue& v = n;
    const char* (Venue::*pick)() const = &Venue::name;
    std::printf("%s\n", (v.*pick)());
    std::printf("%s\n", v.Venue::name());
    std::printf("%zu\n", sizeof(pick));
}
Answer
nasdaq
venue
16

Why. A pointer to a virtual member function does not store an address of Venue::name. It stores "call vtable slot k", so calling it through any object dispatches virtually and reaches Nasdaq::name. The qualified call v.Venue::name() is the one way to suppress virtual dispatch, and it is how an override calls the base version. On the Itanium ABI a member function pointer is two words: a function address or vtable offset, and a this adjustment needed for multiple inheritance. On x86-64 the low bit of the first word marks the virtual case; ARM64 cannot use that bit, so it moves the flag into the adjustment word. That is why it is 16 bytes, cannot be cast to void*, and why std::function or a lambda is usually a simpler table entry. MSVC uses sizes from 8 to 24 bytes depending on the inheritance model.

Find the bugThe program uses a smart pointer, so it must be safe. What does it print, and is it correct?

#include <cstdio>
#include <memory>
#include <string>

struct Message {
    ~Message() { std::puts("~Message"); }
};

struct Quote : Message {
    std::string symbol = "a symbol long enough to live on the heap";
    ~Quote() { std::puts("~Quote"); }
};

int main() {
    std::unique_ptr<Message> m = std::make_unique<Quote>();
}
Answer

Answer. It typically prints only ~Message, and the behaviour is undefined. unique_ptr<Message> uses default_delete<Message>, which runs delete on a Message*. Deleting a derived object through a base pointer whose destructor is not virtual is undefined ([expr.delete]). In practice ~Quote never runs and the heap buffer of symbol leaks.

Fix. Give Message a virtual destructor, or a protected non-virtual one so that deletion through the base does not compile. Two traps live here: the converting constructor from unique_ptr<Quote> compiles without complaint, and GCC's -Wdelete-non-virtual-dtor stays quiet because Message has no virtual functions at all. shared_ptr behaves differently, because it captures the deleter when the first owner is created (Ch 9).

Find the bugWhy does this clone() override fail to compile, and what is the idiomatic fix?

#include <memory>

struct Shape {
    virtual ~Shape() = default;
    virtual std::unique_ptr<Shape> clone() const = 0;
};

struct Circle : Shape {
    std::unique_ptr<Circle> clone() const override { return std::make_unique<Circle>(*this); }
};

int main() {
    Circle c;
    auto p = c.clone();
    return p ? 0 : 1;
}
Answer

Answer. Covariant return types only work for raw pointers and references to classes ([class.virtual]). unique_ptr<Circle> and unique_ptr<Shape> are unrelated class types, even though one converts to the other, so the override's return type is invalid.

Fix. Return std::unique_ptr<Shape> from every override, which is enough in most code. If callers need the precise type, keep a private virtual Circle* clone_impl() const (raw pointers are covariant) and give each class a public non-virtual clone() that wraps it in the right unique_ptr. Many candidates think templates or auto can make the override work. They cannot, because virtual functions cannot be templates and an override cannot have a deduced return type.

OutputHow big is each closure on a 64-bit GCC or Clang target? What does the size of by_ref tell you?

#include <cstdio>
#include <string>

int main() {
    int qty = 100, side = 1;
    double px = 101.25;
    std::string venue = "XNAS";
    auto none = [] { return 0; };
    auto by_ref = [&qty, &side] { return qty * side; };
    auto by_val = [qty, side] { return qty * side; };
    auto mixed = [side, px] { return side * px; };
    auto owns = [venue] { return venue.size(); };
    std::printf("none=%zu by_ref=%zu by_val=%zu mixed=%zu owns_string=%d\n", sizeof none, sizeof by_ref,
                sizeof by_val, sizeof mixed, sizeof owns == sizeof(std::string));
    return none() + by_ref() + by_val() + static_cast<int>(mixed() + owns()) > 0 ? 0 : 1;
}
Answer
none=1 by_ref=16 by_val=8 mixed=16 owns_string=1

Why. A lambda is an unnamed class with one data member per captured entity ([expr.prim.lambda.capture]). With no captures it is an empty class of size 1, because every object needs a distinct address. Two ints take 8 bytes, and int plus double is padded to 16 by alignment. A by-value std::string capture holds a whole std::string (32 bytes in libstdc++ and 24 in libc++, which is why the program compares instead of printing). The layout of reference captures is unspecified, but GCC and Clang store one pointer per reference, so by_ref is two pointers. The wrong answers are "0, references are free" and "8, the size of two ints".

Two consequences. A by-reference closure is a bundle of pointers into the current stack frame, so storing it beyond the frame (in a std::function, a thread or a callback list) is the returned-pointer-to-a-local bug in disguise. And size decides allocation: libstdc++'s std::function stores a closure inline only if it is trivially copyable and at most 16 bytes, and libc++ allows somewhat larger nothrow-movable closures. Anything bigger is heap-allocated on construction and on every copy (Ch 16).

Find the bugA hot path duplicates quotes with memcpy "because it is faster than the copy constructor". It prints the right line. What happens next?

#include <cstdio>
#include <cstring>
#include <string>

struct Quote {
    std::string symbol;
    double px = 0;
};

int main() {
    Quote a{"a symbol name long enough to need the heap", 101.25};
    Quote b;
    std::memcpy(&b, &a, sizeof a);
    std::printf("%s %.2f\n", b.symbol.c_str(), b.px);
}
Answer

Answer. A double free when main returns. memcpy copied the string object's bytes, including the pointer to its heap buffer, so a.symbol and b.symbol both own the same buffer and both destructors free it. ASan reports attempting double-free. The print is correct, which is why the bug survives code review.

Why. memcpy and memset are valid only for trivially copyable types ([basic.types.general]). Quote has a std::string member, so its copy is a real function that allocates. With a short symbol the bug changes shape: libstdc++ strings in SSO mode point at their own inline buffer, so b.symbol would point into a and break as soon as a changes or dies. GCC warns with -Wclass-memaccess, and the warning is right. If the copy is genuinely hot, make the type trivially copyable: store the symbol as a fixed char[8] or a small integer id, then static_assert(std::is_trivially_copyable_v<Quote>), and plain assignment compiles to the same memcpy anyway.

OutputThe same three lines are written for vector<bool> and for vector<int>. What prints?

#include <cstdio>
#include <vector>

int main() {
    std::vector<bool> flags{true, true};
    auto f = flags[0];
    flags[0] = false;

    std::vector<int> nums{1, 1};
    auto n = nums[0];
    nums[0] = 0;

    std::printf("%d %d\n", static_cast<int>(f), n);
}
Answer
0 1

Why. vector<bool> is a specialisation that packs bits, so operator[] cannot return bool&. It returns a proxy object, vector<bool>::reference, that holds a word pointer and a bit mask. auto f deduces that proxy type, so f still refers to bit 0 and sees the later write. For vector<int>, auto n is a plain int copy.

Other consequences: bool* p = &flags[0]; does not compile, flags.data() does not exist, and two threads writing different elements race because they share a word (unlike every other vector<T>). Write bool f = flags[0]; to get a value. If you need real bools, use std::vector<char>, std::deque<bool> or std::unique_ptr<bool[]>.

OutputA buffer is passed to a function that "takes an array of 16 ints". What are the three sizes?

#include <cstddef>
#include <cstdio>

static void fill(int buf[16]) { std::printf("inside %zu\n", sizeof(buf)); }

template <std::size_t N>
static void fill_ref(int (&buf)[N]) { std::printf("ref %zu\n", sizeof(buf)); }

int main() {
    int data[16] = {};
    std::printf("outside %zu\n", sizeof(data));
    fill(data);
    fill_ref(data);
}
Answer
outside 64
inside 8
ref 64

Why. A function parameter declared as an array is adjusted to a pointer ([dcl.fct]), and the 16 is ignored completely. Inside fill, buf is an int*, so sizeof gives the pointer size. Passing a reference to an array keeps the type and lets a template deduce N. In networking code this bug looks like recv(fd, buf, sizeof buf, 0) inside a helper, which silently reads 8 bytes at a time. Both compilers warn (-Wsizeof-array-argument). Pass std::span<int> to carry the size explicitly.

TrickyA host loads a pricing plugin with dlopen, gets a std::unique_ptr<Pricer> from its factory, and unloads the plugin with dlclose during reconfiguration. The process crashes later, when the unique_ptr goes out of scope. Why there?

Answer

Answer. The object outlives the code that defines it. Its vptr points at a vtable inside the plugin, and its virtual destructor is code inside the plugin. Once dlclose unmaps the library, deleting the object jumps into unmapped memory (a SIGSEGV) or into whatever was mapped there since. Any function pointer, std::function target, string literal or type_info that came from the plugin dangles in the same way. dlclose has also run the plugin's static destructors, so plugin globals the object relies on are gone.

Why. Code must outlive every object that uses it, so the library handle needs an owner too. Fixes: return std::shared_ptr<Pricer> whose deleter captures a shared_ptr to the library handle (the library is closed by the last object's deleter); destroy every plugin object before calling dlclose; or never unload (RTLD_NODELETE, which many production systems choose). The crash can depend on the build, because glibc may decline to unmap a library at all, for example when it defines STB_GNU_UNIQUE symbols, which GCC emits for some inline and template statics. The wrong answer blames unique_ptr: any owner would crash, because the bug is the order of two lifetimes.

OutputOrder has a class-specific operator new that counts pool allocations. Which of the three factories go through it?

#include <cstdio>
#include <memory>
#include <new>

struct Order {
    static inline int pool_allocs = 0;
    long id = 0;
    static void* operator new(std::size_t n) {
        ++pool_allocs;
        return ::operator new(n);
    }
    static void operator delete(void* p) { ::operator delete(p); }
};

int main() {
    std::unique_ptr<Order> a(new Order);
    std::printf("new: %d\n", Order::pool_allocs);
    auto b = std::make_unique<Order>();
    std::printf("make_unique: %d\n", Order::pool_allocs);
    auto c = std::make_shared<Order>();
    std::printf("make_shared: %d\n", Order::pool_allocs);
}
Answer
new: 1
make_unique: 2
make_shared: 2

Why. make_unique<Order>() is defined as unique_ptr<Order>(new Order()), so the class-specific operator new is found by the new-expression. make_shared needs one block that holds the control block and the object, so it allocates that block through std::allocator (which calls ::operator new) and constructs Order inside it with placement new. The class's allocator is bypassed completely. In a trading system that relies on class-level pools to avoid the global heap on the hot path, a single make_shared quietly reintroduces malloc.

Fixes: use std::allocate_shared with an allocator that draws from the same pool (it must allocate the combined block, so its size is larger than sizeof(Order)), or use std::shared_ptr<Order>(new Order) and accept the separate control block allocation, which still goes to the global heap. Pool design is covered in Ch 13.

TrickyLegacy code does auto* p = static_cast<Order*>(std::malloc(sizeof(Order))); p->symbol = "AAPL"; where Order has a std::string member. It "works" in testing. What is actually happening?

Answer

Answer. Undefined behaviour. malloc returns raw bytes, and no Order or std::string object exists there. p->symbol = "AAPL" calls string::operator= on garbage: it reads an uninitialised data pointer and size, and may free or write through a random address. It seems to work when the bytes happen to look like an empty short string.

Why. Allocation and construction are separate steps. new does both, malloc does only the first. The fix is placement new, Order* p = new (mem) Order;, and later p->~Order(); std::free(mem); (Ch 12). C++20 lets malloc implicitly create objects of implicit-lifetime types (trivial types such as int arrays or plain structs, P0593), which is why the same code is fine for a struct of ints. A class with a std::string member is not implicit-lifetime.

Find the bugThe constructor moves the symbol into the member and records its width for column alignment. Every width prints as 0. Why, and why does swapping the two initialisers in the list not help?

#include <cstdio>
#include <string>
#include <utility>

class Instrument {
public:
    explicit Instrument(std::string symbol)
        : symbol_(std::move(symbol)), width_(symbol.size()) {}
    void show() const { std::printf("symbol=%s width=%zu\n", symbol_.c_str(), width_); }

private:
    std::string symbol_;
    std::size_t width_;
};

int main() {
    Instrument("VOD.L").show();
    Instrument("BRK.A-long-composite-symbol-name").show();
}
Answer
symbol=VOD.L width=0
symbol=BRK.A-long-composite-symbol-name width=0

Answer. Members are initialised in declaration order, so symbol_ comes first, and its initialiser moves from the parameter. When width_(symbol.size()) runs, symbol is a moved-from string. That is "valid but unspecified", and both libstdc++ and libc++ leave it empty, for short (SSO) and long strings alike. Reordering the mem-initialisers in the source changes nothing, because the order is fixed by the member declarations ([class.base.init]). GCC and Clang warn with -Wreorder when the two orders differ, which is the only hint you get.

Fix. Read from the member, which already exists: width_(symbol_.size()), correct only because symbol_ is declared first. Or compute from the parameter before any move, or move in the constructor body. The rule: once a parameter appears inside std::move in an initialiser list, it must not appear again later in that list. clang-tidy's bugprone-use-after-move catches it. The same declaration-order rule decides when a std::thread member starts running relative to the members it uses.

Trickystd::vector<std::atomic<int>> slots(8); compiles and works as a table of per-venue counters. Someone adds slots.resize(16) and the build breaks. Why does one compile and not the other, and what are the options?

#include <atomic>
#include <deque>
#include <vector>

int main() {
    std::vector<std::atomic<int>> slots(8);  // fine: elements built in place
    std::deque<std::atomic<int>> more;
    more.emplace_back(1);                     // fine: a deque never relocates
    slots.resize(16);                         // error: needs to move elements
    return slots[0] + more[0];
}
Answer

Answer. std::atomic can be neither copied nor moved. The size constructor only value-initialises elements in place, which atomic supports. resize, reserve, push_back, emplace_back and insert may reallocate, and reallocation relocates the existing elements by moving or copying them, so these members require the element type to be MoveInsertable. The check is at compile time, so the build fails even if the capacity would have sufficed. std::mutex, std::condition_variable and any class holding one behave the same way.

Why. It is also the right outcome for threads: relocating an atomic while other threads use it can never be made safe. Options: size the table once and never grow it; use std::deque<std::atomic<int>> with emplace_back, which only constructs in place because a deque never relocates existing elements; use std::unique_ptr<std::atomic<int>[]>; or wrap each atomic in a struct with a copy constructor that loads and stores, which is safe only while no other thread is touching the table. For per-thread counters, also pad each slot to a cache line (Ch 17). The wrong answer is "atomic has no default constructor": it has one, and since C++20 it value-initialises the value (P0883).

OutputWhich overload does each call pick?

#include <cstdio>
#include <string>
#include <utility>

static void take(const std::string&) { std::puts("lvalue"); }
static void take(std::string&&) { std::puts("rvalue"); }

int main() {
    std::string&& r = std::string("tmp");
    take(r);
    take(std::move(r));
    take(static_cast<decltype(r)>(r));
    auto&& fwd = r;
    take(std::forward<decltype(fwd)>(fwd));
}
Answer
lvalue
rvalue
rvalue
lvalue

Why. A named variable is an lvalue whatever its declared type, so take(r) picks the const& overload even though r is an rvalue reference. decltype(r) is std::string&&, so the cast produces an xvalue, which is all std::move does. auto&& fwd = r binds a forwarding reference to the lvalue r, so fwd's type is std::string& and std::forward returns an lvalue. The answer "rvalue" for the last line comes from forgetting that forwarding preserves the category of the initialiser, and r as an expression is an lvalue.

OutputOrders move from a pending std::set to a send queue, first with std::move on the element and then through extract. Count the copies and moves.

#include <cstdio>
#include <iterator>
#include <set>
#include <string>
#include <utility>
#include <vector>

struct Order {
    static inline int copies = 0, moves = 0;
    std::string id;
    explicit Order(const char* s) : id(s) {}
    Order(const Order& o) : id(o.id) { ++copies; }
    Order(Order&& o) noexcept : id(std::move(o.id)) { ++moves; }
    bool operator<(const Order& o) const { return id < o.id; }
};

int main() {
    std::set<Order> pending;
    pending.emplace("ord-0001-with-a-long-client-tag");
    pending.emplace("ord-0002-with-a-long-client-tag");
    std::vector<Order> sent;
    sent.reserve(2);

    sent.push_back(std::move(*pending.begin()));
    std::printf("move from set element: copies=%d moves=%d\n", Order::copies, Order::moves);

    auto node = pending.extract(std::next(pending.begin()));
    sent.push_back(std::move(node.value()));
    std::printf("move from extracted node: copies=%d moves=%d\n", Order::copies, Order::moves);
    std::printf("set size=%zu\n", pending.size());
}
Answer
move from set element: copies=1 moves=0
move from extracted node: copies=1 moves=1
set size=1

Why. Elements of a std::set (and keys of a std::map) are const, because changing one in place would break the tree's ordering. *pending.begin() is a const Order&, std::move turns it into const Order&&, and that binds only to the copy constructor. So the first "move" is a silent copy, and the element also stays in the set. C++17's extract unlinks the node and returns a node handle that owns it, and node.value() gives non-const access, so the second move really moves. The common wrong answer is "copies=0 moves=2": std::move never casts away const.

Node handles have two more uses interviewers like: other.insert(std::move(node)) transfers an element between sets or maps without allocating, and auto nh = m.extract(k); nh.key() = k2; m.insert(std::move(nh)); changes a map key in place. The same trap appears in for (auto& [k, v] : m) out.push_back(std::move(k));, which copies every key while really moving every value.

Find the bugThe lambda owns the order through an init-capture and should hand it back. Why does it not compile?

#include <memory>
#include <utility>

int main() {
    auto order = std::make_unique<int>(42);
    auto task = [o = std::move(order)]() { return std::move(o); };
    auto back = task();
    return *back == 42 ? 0 : 1;
}
Answer

Answer. A lambda's operator() is const unless the lambda is mutable, so inside the body o is a const std::unique_ptr<int>. std::move(o) yields const unique_ptr&&, which can only bind to the deleted copy constructor. Both compilers report a call to a deleted function.

Fix. Write [o = std::move(order)]() mutable { return std::move(o); }. This is the lambda version of the const-member trap, where a move silently becomes a copy (Ch 18). With a copyable type such as std::string it would compile and silently copy instead of failing, which is worse. A lambda holding a unique_ptr is move-only, so it cannot be stored in std::function. Use C++23 std::move_only_function or a template parameter.

ConceptWhat does std::swap(a, b) cost for a type with a copy constructor and no move constructor, and why do libraries provide a member swap or a hidden friend?

Answer

Answer. The generic std::swap is T tmp = std::move(a); a = std::move(b); b = std::move(tmp);. With no move operations, all three steps copy, so swapping two large buffers costs three deep copies and two allocations. A type-specific swap exchanges the internal pointers in O(1) and cannot throw.

Why. Generic code calls using std::swap; swap(a, b); so argument-dependent lookup finds a better overload in the type's namespace (a hidden friend is found only that way, which keeps overload sets small). A noexcept swap is the building block for copy-and-swap assignment and for the strong exception guarantee. With a proper noexcept move constructor and move assignment, the generic version is already cheap, and a custom swap only saves a few pointer writes.

What the standard says vs what the compiler does

Drills

Here "it printed X on my machine" and "the language guarantees X" are different answers. Know which category each result falls into: defined, unspecified, implementation-defined or undefined.

OutputWhat does show(next(), next()) print?

#include <cstdio>

static int counter = 0;
static int next() { return ++counter; }
static void show(int a, int b) { std::printf("%d %d\n", a, b); }

int main() {
    show(next(), next());
}
Answer

Answer. Either 1 2 or 2 1, and both are correct. The order in which function arguments are evaluated is unspecified ([expr.call]). On this guide's ARM64 test machine both GCC and Clang print 1 2, but GCC on x86-64 has historically evaluated many argument lists right to left, and the order may change with the optimisation level, the argument types or the compiler version. The output is not compared for that reason.

Why. Unspecified is not undefined: since C++17 each argument is evaluated completely before the next one starts (they are indeterminately sequenced), so the program is valid and prints one of the two results. Before C++17 the sub-expressions of different arguments could interleave, which made f(std::unique_ptr<T>(new T), g()) leak if g() threw between the new and the unique_ptr constructor. That leak is gone in C++17. If the order matters, evaluate into named locals first.

OutputSame counter, now with stream insertion and with a map assignment. What does C++20 guarantee?

#include <iostream>
#include <map>

int main() {
    std::cout << next() << ' ' << next() << ' ' << next() << '\n';
    std::map<int, int> m;
    m[next()] = next();
    std::cout << m.begin()->first << ' ' << m.begin()->second << '\n';
}
Answer
1 2 3
5 4

Why. C++17 (P0145) added sequencing rules for a few operators. In E1 << E2 and E1 >> E2, E1 is sequenced before E2, so chained stream output now runs left to right even though each << is a function call. In assignment E1 = E2 (and compound assignment), the right operand is sequenced before the left, so the value next() runs first and returns 4, then the key next() returns 5. In C++14 both lines were unspecified, so a compiler could legally print 3 2 1 for the first one, and older compilers sometimes did. The same rule makes v[i] = i++; well defined since C++17, and explains why m[k] = m.size(); stores the size before the insertion.

OutputAn overflow guard: will_grow(INT_MAX) should return false. What does an optimising compiler make of it?

#include <climits>
#include <cstdio>

static bool will_grow(int x) { return x + 1 > x; }

int main(int argc, char**) {
    int big = INT_MAX - 1 + argc;  // INT_MAX when run with no arguments
    std::printf("%d\n", will_grow(big));
}
Answer

Answer. With optimisation, both GCC and Clang compile will_grow to return true and print 1. Without optimisation you may see 0, because the addition wraps on the hardware. The output is not compared here because the program has undefined behaviour.

Why. Signed overflow is undefined ([expr.pre]), so the compiler may assume it never happens, and then x + 1 > x is always true. This is how loops like for (int i = 0; i >= 0; ++i) become infinite and how overflow checks written after the fact disappear. Correct guards test before the operation: x < INT_MAX, or __builtin_add_overflow(x, 1, &out), or C++26 std::add_sat. Unsigned arithmetic wraps by definition, and -fwrapv makes signed wrap too, at some cost to loop optimisation. UBSan (-fsanitize=signed-integer-overflow) catches it at run time.

OutputAre these two lines undefined behaviour in C++20? If not, what do they print?

#include <cstdio>

int main() {
    int i = 5;
    i = i++ + 1;
    int k = 1;
    k += k++;
    std::printf("%d %d\n", i, k);
}
Answer
6 3

Why. Both were undefined before C++11 and still undefined in C++14, because the side effect of i++ and the assignment to i were unsequenced. Since C++17 the right operand of every assignment, including compound assignment, is sequenced before the left operand and before the assignment itself. So i++ + 1 is fully evaluated (value 6, and i becomes 6), then 6 is stored. For k += k++, the right side yields 1 and sets k to 2, then k = k + 1 gives 3. i++ + i++ and f(i++, i++) are still not defined the way people hope: the first is undefined, the second unspecified. Never write this in real code, but know why it is legal now.

Trickychar c = '\xFF'; if (c < 0) ... takes the branch on an x86-64 Linux box and not on an ARM64 Linux box. Which compiler is wrong?

Answer

Answer. Neither. Whether plain char is signed is implementation-defined, and the ABI decides. x86-64 Linux, Windows and Apple's ARM64 ABI use signed char. The standard ARM64 Linux (AAPCS64), 32-bit ARM Linux and POWER ABIs use unsigned char. char, signed char and unsigned char are three distinct types in every case.

Why. This bites parsers that index tables with a char (a negative index on x86, fine on ARM) and checksum code that adds bytes. Use unsigned char or std::uint8_t for raw bytes, or std::byte, and convert explicitly. -funsigned-char and -fsigned-char change the default and break ABI compatibility with other libraries. Other implementation-defined favourites: sizeof(long) (8 on Linux, 4 on Windows) and right shift of a negative number (arithmetic on every mainstream compiler, and defined that way since C++20).

OutputTwo ways to look at the bits of a float. What prints, and which commonly used third way is undefined?

#include <bit>
#include <cstdint>
#include <cstdio>
#include <cstring>

    auto viaBitCast = std::bit_cast<std::uint32_t>(f);
    std::uint32_t viaMemcpy;

    std::printf("%08x %08x\n", viaBitCast, viaMemcpy);

3f800000 3f800000

Why. IEEE 754 single precision stores 1.0 as sign 0, biased exponent 127 (0x7f) and fraction 0, which is 0x3f800000. Both ways copy the object representation, which is well defined. The undefined way is *reinterpret_cast<std::uint32_t*>(&f): it reads a float object through a uint32_t glvalue, which breaks the strict aliasing rule ([basic.lval]). The optimiser assumes that an int* and a float* never refer to the same object, and may reorder or delete the accesses. Union type punning is allowed in C but is undefined in C++, although GCC documents it as an extension. memcpy of 4 bytes compiles to a single register move, so the safe versions cost nothing. std::bit_cast (C++20) is also constexpr.

ConceptWhat does the inline keyword actually guarantee in modern C++? Does it make a function get inlined?

Answer

Answer. inline is about the one-definition rule, not about inlining. An inline function or (since C++17) inline variable may be defined in several translation units, as long as every definition is token-for-token identical, and the linker keeps one copy. Whether a call is expanded in place is the optimiser's choice, and it inlines non-inline functions and ignores the keyword freely.

Why. It is what lets you define functions in headers. Member functions defined inside a class body, constexpr functions and function templates are implicitly inline. The trap is the "identical" requirement: two TUs that see different definitions (different #defines, or two unrelated classes both called Node in the global namespace) cause an ODR violation, which is undefined behaviour with no diagnostic required. The linker silently keeps one version. Put file-local helpers in an anonymous namespace or mark them static. To force or block inlining, use [[gnu::always_inline]] or [[gnu::noinline]].

Find the bugThe destructor reports flush failures by throwing, and it is explicitly marked noexcept(false). What happens when an order fails?

#include <cstdio>
#include <stdexcept>

struct Flusher {
    ~Flusher() noexcept(false) {
        std::puts("flush failed, throwing");
        throw std::runtime_error("disk full");
    }
};

int main() {
    try {
        Flusher f;
        throw std::runtime_error("bad order");
    } catch (const std::exception& e) {
        std::printf("caught %s\n", e.what());
    }
}
Answer

Answer. std::terminate is called and the program aborts. The catch never runs. Even the puts line may not appear when stdout is a pipe, because abort does not flush stdio buffers.

Why. Throwing bad order starts stack unwinding, which destroys f. If a destructor called during unwinding exits with an exception, there would be two exceptions in flight, and C++ handles that by calling std::terminate ([except.terminate]). Without the noexcept(false) it is even worse: destructors are implicitly noexcept, so any throw out of them terminates, unwinding or not (GCC warns with -Wterminate). Fix: never let exceptions escape a destructor. Provide an explicit flush() or close() that can throw, and have the destructor call it inside try { } catch (...) { } as a best-effort fallback. std::uncaught_exceptions() lets a destructor know whether it is running because of unwinding, which the Transaction exercise below uses.

Rapid-fire one-liners

Drills

Screening rounds often open with a burst of these. Aim to answer each in one sentence and then give the reason in a second sentence if asked.

ConceptCan you overload a function on its return type alone?

Answer

Answer. No. Overloads must differ in their parameter lists (including const/ref qualifiers on member functions).

Why. A call expression has to be resolved without knowing what the result is used for, and the result may be discarded. Return types only enter the signature of function templates, and a conversion operator template can fake "overload on return type" when that is really needed.

TrickyWhat does delete p; do when p is null, and what does free(nullptr) do?

Answer

Answer. Nothing in both cases. They are defined no-ops, so if (p) delete p; is redundant.

Why. The real danger is the opposite case, a non-null pointer that was already deleted. Setting a pointer to null after delete turns a later double delete into a harmless no-op, but it also hides the logic error. Smart pointers remove the question entirely.

ConceptWhy is std::endl slower than '\n' in a loop that writes a million lines to a file?

Answer

Answer. std::endl writes a newline and flushes the stream, so each line becomes a separate write system call. '\n' just appends to the buffer.

Why. A million syscalls cost far more than the formatting. For a terminal, std::cout is often line buffered anyway, which hides the difference in tests. Use '\n' and flush explicitly where you need durability or interactivity.

ConceptWhat is the largest payload of a single UDP datagram over IPv4, and what actually limits it in practice?

Answer

Answer. 65507 bytes: the 16-bit IP total length (65535) minus the 20-byte IP header and the 8-byte UDP header. In practice anything above the path MTU (about 1472 bytes of payload on Ethernet) is fragmented, and losing one fragment loses the whole datagram.

Why. Market data protocols keep datagrams under the MTU for this reason. If the receive buffer is smaller than the datagram, recv truncates it and the rest is discarded (MSG_TRUNC tells you).

TrickyCan you re-seat a reference, for example inside a class's copy assignment operator?

Answer

Answer. No. Assigning to a reference assigns to the object it refers to. That is why a class with a reference member gets a deleted copy assignment operator.

Why. If you need a rebindable reference, store a pointer or std::reference_wrapper<T>, which is also what lets containers hold "references".

ConceptWhich ephemeral port range does Linux use for outgoing connections by default?

Answer

Answer. 32768 to 60999, set by net.ipv4.ip_local_port_range. IANA recommends 49152 to 65535, which Windows and macOS use.

Why. The range limits how many concurrent connections one client address can open to one server address and port, together with TIME_WAIT. See the TIME_WAIT drill in the networking section.

TrickyIs sizeof('a') the same in C and C++?

Answer

Answer. No. In C++ a character literal has type char, so the size is 1. In C it has type int, so the size is usually 4.

Why. C++ changed the type so that overloads such as print(char) and print(int) pick the right one for print('a'). It is a classic question about why C++ is not a superset of C, along with void* needing a cast and auto meaning something else.

Write the code: cross-topic exercises

Coding

Each exercise fixes one of the traps above properly. Interviewers grade the edge cases as much as the happy path, so each answer lists the pitfalls they look for.

CodeWrite BitVector, a packed bit array with a proxy reference, and get the proxy's assignment right.

Store bits in std::uint64_t words. Support push_back(bool), size(), count(), a const operator[] returning bool, and a non-const operator[] returning a proxy that supports b[i] = true, b[i] = b[j], conversion to bool and flip(). Explain what auto r = b[i]; means for your users.

Answer

Approach. The proxy holds a pointer to one word and a single-bit mask. Assigning a bool sets or clears the bit. The proxy's copy assignment is the subtle part: b[i] = b[j] must copy the bit value, so it is written as "convert the source to bool, then assign", whereas the defaulted version would re-point the proxy and leave the vector unchanged. count() uses std::popcount per word, which works because unused high bits of the last word are kept at zero.

#include <bit>
#include <cstddef>
#include <cstdint>
#include <cstdio>
#include <vector>

class BitVector {
public:
    class reference {
    public:
        reference(std::uint64_t& word, std::uint64_t mask) : w_(&word), m_(mask) {}
        reference(const reference&) = default;
        reference& operator=(bool b) {
            if (b) *w_ |= m_; else *w_ &= ~m_;
            return *this;
        }
        reference& operator=(const reference& other) { return *this = static_cast<bool>(other); }
        operator bool() const { return (*w_ & m_) != 0; }
        void flip() { *w_ ^= m_; }

    private:
        std::uint64_t* w_;
        std::uint64_t m_;
    };

    explicit BitVector(std::size_t n = 0) : words_((n + 63) / 64), size_(n) {}

    void push_back(bool b) {
        if (size_ % 64 == 0) words_.push_back(0);
        ++size_;
        (*this)[size_ - 1] = b;
    }
    reference operator[](std::size_t i) { return reference(words_[i / 64], std::uint64_t{1} << (i % 64)); }
    bool operator[](std::size_t i) const { return (words_[i / 64] >> (i % 64)) & 1u; }
    std::size_t size() const { return size_; }
    std::size_t count() const {
        std::size_t c = 0;
        for (std::uint64_t w : words_) c += static_cast<std::size_t>(std::popcount(w));
        return c;
    }

private:
    std::vector<std::uint64_t> words_;
    std::size_t size_;
};

int main() {
    BitVector b(70);
    b[3] = true;
    b[69] = true;
    b[64] = b[3];   // copies the bit, not the proxy
    auto r = b[5];  // r is a proxy: writing through it changes b
    r = true;
    b[69].flip();
    b.push_back(true);
    const BitVector& cb = b;
    std::printf("size=%zu count=%zu b5=%d b64=%d b69=%d b70=%d\n",
                cb.size(), cb.count(), cb[5], cb[64], cb[69], cb[70]);
}
size=71 count=4 b5=1 b64=1 b69=0 b70=1

Complexity and pitfalls. Element access is O(1) with a shift and a mask, and count() is O(n/64). Pitfalls that interviewers probe: the defaulted proxy assignment (silently does nothing to the vector), auto r = b[i] holding a proxy that dangles once push_back reallocates words_, generic code that expects T& (bool& x = b[i] fails to compile), and concurrency: two threads writing different bits of the same word race, which is never true for distinct elements of an ordinary vector. These are exactly the reasons std::vector<bool> is considered a design mistake. A resize that shrinks must also clear the bits above the new size, or count() breaks.

Estimated rating: ~1600 · easy bit arithmetic, but the proxy's copy assignment and lifetime are a real test.

CodeImplement Lazy<T>: a correct double-checked lazy initialiser.

T& get(F make) builds the value with make() on first use and returns it. It must be safe when many threads call it at once, make must run exactly once, and the fast path after initialisation must take no lock. The destructor frees the value.

Answer

Approach. Store the pointer in a std::atomic<T*>. The fast path is an acquire load: if it sees the pointer, it also sees everything the constructor wrote, because the writer published the pointer with a release store after construction. The slow path takes a mutex and checks again, so only one thread builds the value. Inside the lock the re-check can be relaxed, since the mutex already orders it after any earlier publisher.

#include <atomic>
#include <cstdio>
#include <mutex>
#include <string>
#include <thread>
#include <vector>

template <class T>
class Lazy {
public:
    Lazy() = default;
    Lazy(const Lazy&) = delete;
    Lazy& operator=(const Lazy&) = delete;
    ~Lazy() { delete ptr_.load(std::memory_order_relaxed); }

    template <class F>
    T& get(F&& make) {
        if (T* p = ptr_.load(std::memory_order_acquire)) return *p;
        std::lock_guard<std::mutex> lock(mtx_);
        T* p = ptr_.load(std::memory_order_relaxed);
        if (!p) {
            p = new T(make());
            ptr_.store(p, std::memory_order_release);
        }
        return *p;
    }

private:
    std::atomic<T*> ptr_{nullptr};
    std::mutex mtx_;
};

int main() {
    Lazy<std::string> config;
    std::atomic<int> builds{0};
    std::atomic<std::size_t> total{0};
    std::vector<std::thread> ts;
    for (int i = 0; i < 8; ++i)
        ts.emplace_back([&] {
            const std::string& c = config.get([&] {
                builds.fetch_add(1, std::memory_order_relaxed);
                return std::string("venue=XNAS depth=10");
            });
            total.fetch_add(c.size(), std::memory_order_relaxed);
        });
    for (auto& t : ts) t.join();
    std::printf("builds=%d total=%zu\n", builds.load(), total.load());
}
builds=1 total=152

Complexity and pitfalls. After initialisation each call is one acquire load (a plain load on x86, ldar on ARM64). Pitfalls: a plain T* (the original bug), relaxed on the fast path (no visibility of the constructed object), publishing the pointer before construction finishes, and an exception from make(): here it propagates, the lock is released by RAII and the next caller retries, which is the same behaviour as a function-local static. In real code a function-local static or std::call_once is simpler. Write this version when the object must be per instance or destroyed at a chosen time.

Estimated rating: ~1700 · short, but needs a precise explanation of acquire/release and of the re-check.

CodeWrite an AsyncLogger that moves log I/O off the hot threads and shuts down safely.

log(std::string) may be called from any thread and must only enqueue. One background thread writes lines to a sink, here a std::vector<std::string>& standing in for a file. The destructor must flush every line logged before it started, join the thread, and never throw or deadlock. Lines from one thread must keep their order.

Answer

Approach. A mutex-protected vector is the queue and a condition variable wakes the worker. The worker swaps the whole queue into a local batch under the lock and writes the batch after unlocking, so slow I/O never blocks producers. The destructor sets stop_ under the lock, notifies and joins, and the worker exits only once it has seen stop_ and found the queue empty, which guarantees the final flush. The thread is declared as the last member, so everything it touches is constructed before it starts and is still alive until it is joined.

#include <condition_variable>
#include <cstdio>
#include <mutex>
#include <string>
#include <thread>
#include <vector>

class AsyncLogger {
public:
    explicit AsyncLogger(std::vector<std::string>& sink) : sink_(sink), worker_([this] { run(); }) {}
    AsyncLogger(const AsyncLogger&) = delete;
    AsyncLogger& operator=(const AsyncLogger&) = delete;
    ~AsyncLogger() {
        {
            std::lock_guard<std::mutex> g(m_);
            stop_ = true;
        }
        cv_.notify_one();
        worker_.join();
    }

    void log(std::string line) {
        {
            std::lock_guard<std::mutex> g(m_);
            q_.push_back(std::move(line));
        }
        cv_.notify_one();
    }

private:
    void run() {
        std::vector<std::string> batch;
        std::unique_lock<std::mutex> lk(m_);
        for (;;) {
            cv_.wait(lk, [this] { return stop_ || !q_.empty(); });
            batch.swap(q_);
            const bool stopping = stop_;
            lk.unlock();
            for (auto& s : batch) sink_.push_back(std::move(s));  // the slow part, unlocked
            batch.clear();
            lk.lock();
            if (stopping && q_.empty()) return;
        }
    }

    std::vector<std::string>& sink_;
    std::mutex m_;
    std::condition_variable cv_;
    std::vector<std::string> q_;
    bool stop_ = false;
    std::thread worker_;  // last: starts after, and is joined before, everything it uses
};

int main() {
    std::vector<std::string> sink;
    {
        AsyncLogger logger(sink);
        std::vector<std::thread> ts;
        for (int t = 0; t < 4; ++t)
            ts.emplace_back([&logger, t] {
                for (int i = 0; i < 250; ++i)
                    logger.log(std::to_string(t) + ":" + std::to_string(i));
            });
        for (auto& th : ts) th.join();
    }  // destructor flushes and joins
    int last[4] = {-1, -1, -1, -1};
    bool ordered = true;
    for (const auto& line : sink) {
        int t = line[0] - '0';
        int i = std::stoi(line.substr(2));
        ordered = ordered && i == last[t] + 1;
        last[t] = i;
    }
    std::printf("lines=%zu per-thread order kept=%d\n", sink.size(), ordered);
}
lines=1000 per-thread order kept=1

Complexity and pitfalls. Each log is one short critical section, and the worker takes the lock once per batch rather than once per line. Pitfalls: writing to the sink while holding the lock (every producer then waits for the disk), checking stop_ before draining (lines are lost at shutdown), waiting without a predicate (lost and spurious wakeups), declaring the thread before the queue or mutex (members are initialised in declaration order, as the width bug in the move section shows), and calling log from a destructor of a static object after the logger is gone. A low-latency version replaces the mutex with a per-thread SPSC ring, formats lazily, and bounds the queue, choosing between blocking and dropping when it is full.

Estimated rating: ~1600 · standard producer and consumer code, judged on the shutdown path and on doing I/O outside the lock.

CodeWrite Synchronized<T>, a value that can only be reached while its mutex is held.

Provide lock(), which returns a proxy that holds the lock and gives -> and * access, and with(f), which calls f(value) under the lock and returns its result. There must be no way to reach the value without locking. Test with four threads appending to a Synchronized<std::vector<int>>.

Answer

Approach. The value and its mutex are private members of the same object, so the only doors are the two accessors. The proxy owns a std::unique_lock and a reference to the value, and it is returned by value, which C++17 guaranteed elision constructs directly in the caller. with takes a scoped_lock and forwards f, and decltype(auto) preserves a returned reference or value exactly.

#include <cstdio>
#include <mutex>
#include <thread>
#include <utility>
#include <vector>

template <class T>
class Synchronized {
public:
    template <class... Args>
    explicit Synchronized(Args&&... args) : value_(std::forward<Args>(args)...) {}

    class Locked {
    public:
        Locked(std::mutex& m, T& v) : lock_(m), v_(v) {}
        T* operator->() const { return &v_; }
        T& operator*() const { return v_; }

    private:
        std::unique_lock<std::mutex> lock_;
        T& v_;
    };

    [[nodiscard]] Locked lock() { return Locked(m_, value_); }

    template <class F>
    decltype(auto) with(F&& f) {
        std::scoped_lock guard(m_);
        return std::forward<F>(f)(value_);
    }

private:
    std::mutex m_;
    T value_;
};

int main() {
    Synchronized<std::vector<int>> fills;
    std::vector<std::thread> ts;
    for (int i = 0; i < 4; ++i)
        ts.emplace_back([&fills, i] {
            for (int k = 0; k < 1000; ++k) fills.lock()->push_back(i);
        });
    for (auto& t : ts) t.join();
    std::size_t n = fills.with([](const std::vector<int>& v) { return v.size(); });
    {
        auto locked = fills.lock();
        locked->push_back(-1);
        std::printf("size=%zu last=%d\n", n, locked->back());
    }
}
size=4000 last=-1

Complexity and pitfalls. One lock per access, so batch work inside one lock() or with rather than locking per element in hot paths. Pitfalls: auto& v = *fills.lock(); compiles and leaves v unprotected, because the proxy (and its lock) dies at the end of the full expression. Returning a reference out of with leaks the value past the lock in the same way. Calling lock() twice on one thread deadlocks, since std::mutex is not recursive. Folly's Synchronized and Boost's synchronized_value are production versions, with shared locks for readers.

Estimated rating: ~1600 · a small template whose value is in the lifetime reasoning about the proxy.

CodeSerialise an order message to a portable wire format and parse it back safely.

The wire format is big-endian and packed: type (1 byte, 'N'), order_id (8), price in units of 1/10000 (signed, 8), qty (4) and side (1 byte, 'B' or 'S'), 22 bytes in all. Write encode(order, buf, len) returning the bytes written (0 if the buffer is too small) and decode(buf, len) returning std::optional<Order>, rejecting short buffers and invalid fields. No packed structs, no casts of the buffer to a struct pointer.

Answer

Approach. Two small templates do every field: put_be writes an unsigned integer most significant byte first with shifts, and get_be reads it back. Shifts work on values, not memory, so the code is correct on any host byte order and needs no htonl (which has no portable 64-bit form). Signed fields go through their unsigned type, a conversion that is well defined both ways since C++20. Decoding checks the length before reading and validates the type and side bytes.

#include <cstddef>
#include <cstdint>
#include <cstdio>
#include <optional>
#include <type_traits>

struct Order {
    std::uint64_t id;
    std::int64_t price;  // 1/10000 units
    std::uint32_t qty;
    char side;
};

constexpr std::size_t kWireSize = 1 + 8 + 8 + 4 + 1;

template <class U>
static unsigned char* put_be(unsigned char* p, U v) {
    static_assert(std::is_unsigned_v<U>);
    for (int i = sizeof(U) - 1; i >= 0; --i) *p++ = static_cast<unsigned char>(v >> (8 * i));
    return p;
}

template <class U>
static const unsigned char* get_be(const unsigned char* p, U& v) {
    v = 0;
    for (std::size_t i = 0; i < sizeof(U); ++i) v = static_cast<U>((v << 8) | *p++);
    return p;
}

static std::size_t encode(const Order& o, unsigned char* buf, std::size_t len) {
    if (len < kWireSize) return 0;
    unsigned char* p = buf;
    *p++ = 'N';
    p = put_be(p, o.id);
    p = put_be(p, static_cast<std::uint64_t>(o.price));
    p = put_be(p, o.qty);
    *p++ = static_cast<unsigned char>(o.side);
    return static_cast<std::size_t>(p - buf);
}

static std::optional<Order> decode(const unsigned char* buf, std::size_t len) {
    if (len < kWireSize || buf[0] != 'N') return std::nullopt;
    Order o{};
    std::uint64_t price = 0;
    const unsigned char* p = buf + 1;
    p = get_be(p, o.id);
    p = get_be(p, price);
    p = get_be(p, o.qty);
    o.price = static_cast<std::int64_t>(price);
    o.side = static_cast<char>(*p);
    if (o.side != 'B' && o.side != 'S') return std::nullopt;
    return o;
}

int main() {
    unsigned char buf[64];
    std::size_t n = encode(Order{12345, 1892500, 100, 'B'}, buf, sizeof buf);
    std::printf("wire size %zu\nbytes:", n);
    for (std::size_t i = 0; i < 9; ++i) std::printf(" %02x", buf[i]);
    std::printf("\n");
    if (auto o = decode(buf, n))
        std::printf("id=%llu px=%lld.%04lld qty=%u side=%c\n",
                    static_cast<unsigned long long>(o->id), static_cast<long long>(o->price / 10000),
                    static_cast<long long>(o->price % 10000), o->qty, o->side);
    std::printf("truncated: %s\n", decode(buf, n - 1) ? "accepted" : "rejected");
    buf[0] = 'X';
    std::printf("bad type: %s\n", decode(buf, n) ? "accepted" : "rejected");
    std::printf("negative price round trip: %s\n",
                decode(buf + 32, encode(Order{1, -5, 1, 'S'}, buf + 32, 32))->price == -5 ? "ok" : "broken");
}

id=12345 px=189.2500 qty=100 side=B

bad type: rejected

Complexity and pitfalls. O(1) per message, and compilers turn the shift loops into a single load or store plus a byte-swap instruction. Pitfalls: send(fd, &order, sizeof order, 0) (padding, host byte order and an information leak, as in the struct drill above), reinterpret_cast of the receive buffer to a struct pointer (strict aliasing and misalignment), reading fields before checking the length, and shifting a signed value. Sequence numbers and a version byte belong in a real header so that a parser can reject messages it does not understand. Exchange protocols such as ITCH and SBE use exactly this kind of fixed layout.

Estimated rating: ~1300 · simple byte handling, judged on endianness, bounds checks and avoiding aliasing tricks.

CodeWrite a Transaction guard that rolls back on failure and never throws from its destructor.

It records operations into a shared log. commit() makes them permanent. If the guard is destroyed without a commit, it removes its operations and reports whether the cause was an exception or a forgotten commit. The destructor must be safe to run during stack unwinding.

Answer

Approach. Remember the log size at construction, and on rollback erase everything after it. To tell "unwinding" from "forgot to commit", compare std::uncaught_exceptions() in the destructor with the value saved in the constructor. Comparing counts (rather than calling the removed std::uncaught_exception()) gives the right answer even when the guard is created inside another object's destructor during unwinding. Nothing in the destructor can throw: erasing strings from the end of a vector never allocates.

#include <cstdio>
#include <exception>
#include <stdexcept>
#include <string>
#include <utility>
#include <vector>

class Transaction {
public:
    explicit Transaction(std::vector<std::string>& log)
        : log_(log), mark_(log.size()), uncaught_(std::uncaught_exceptions()) {}
    Transaction(const Transaction&) = delete;
    Transaction& operator=(const Transaction&) = delete;

    void add(std::string op) { log_.push_back(std::move(op)); }
    void commit() {
        committed_ = true;
        std::printf("committed: %zu ops\n", log_.size() - mark_);
    }
    ~Transaction() {
        if (committed_) return;
        const char* why = std::uncaught_exceptions() > uncaught_ ? "exception" : "no commit";
        std::size_t n = log_.size() - mark_;
        log_.erase(log_.begin() + static_cast<std::ptrdiff_t>(mark_), log_.end());
        std::printf("rolled back %zu ops (%s)\n", n, why);
    }

private:
    std::vector<std::string>& log_;
    std::size_t mark_;
    int uncaught_;
    bool committed_ = false;
};

int main() {
    std::vector<std::string> log;
    {
        Transaction t(log);
        t.add("A1");
        t.add("A2");
        t.commit();
    }
    try {
        Transaction t(log);
        t.add("B1");
        throw std::runtime_error("risk check failed");
    } catch (const std::exception& e) {
        std::printf("caught: %s\n", e.what());
    }
    {
        Transaction t(log);
        t.add("C1");
    }
    std::printf("log:");
    for (const auto& op : log) std::printf(" %s", op.c_str());
    std::printf("\n");
}
committed: 2 ops
rolled back 1 ops (exception)
caught: risk check failed
rolled back 1 ops (no commit)
log: A1 A2

Complexity and pitfalls. Rollback is O(k) in the operations added. The destructor runs before the catch handler, which is why "rolled back" prints first. Pitfalls: doing fallible work (I/O, allocation) in the destructor, using the boolean std::uncaught_exception() (deprecated in C++17 and removed in C++20) which is wrong for nested guards, and letting commit() set the flag before a step that can throw. In a real system commit() is where errors surface and may throw. The destructor's job is only the cleanup that cannot fail. The Library Fundamentals TS calls these scope_success and scope_fail.

Estimated rating: ~1400 · simple bookkeeping, tested on unwinding order and on the no-throw destructor rule.
